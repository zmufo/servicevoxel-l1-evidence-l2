# 体元 × 社区场景：词表域障碍实测记录

**性质**：本文为实测记录，非设计推演。所有数据由 `judge_ten_v2.py` 实跑得出。
**测试对象**：`judge_ten_v2.py` + `冻结件_判据与词表.json`（v2.0 冻结回归原型）
**测试日期**：2026-11-03

---

## 零、一句话结论

> 阻碍体元接入社区场景的，不只是"输入形态"（IoT JSON vs 中文文本），
> 更根本的是**词表域**：当前词表是数据库运维动词表，社区核心动词全部在域外。
> 即使是纯中文文本、含地址与设备编号的物业报修工单，当前原型同样抽不出动作。

**这推翻了"物业报修是最容易落地的第一条链路"这一判断。**

### 1.1 词表实际内容（实测读取）

```

  确认恢复 / confirm_recovery

  查询 / 排查 / 只读 / 检查 / 核对 / 检索 / 探测 / 探针 / 健康 / 日志
  连通性 / 监控 / 观测 / 可观测性 / 人工介入 / 上报 / 汇总 / 交叉验证 / 核实 / 验证
```

**全部为数据库/运维领域动词。**

### 1.2 测试结果（6 条，实测输出）

| 场景 | 文本 | danger | safe | 可判定类别 |
|---|---|---|---|---|
| 楼道灯维修 | A栋3单元楼道灯坏了，请派电工上门维修。 | `[]` | `[]` | **NONE** |
| 电梯检修 | 3号楼电梯坏了，请立即派人检修。 | `[]` | `[]` | **NONE** |
| 井盖更换 | 请更换5号楼2单元的损坏井盖。 | `[]` | `[]` | **NONE** |
| 垃圾清运 | 居民反映垃圾桶满溢，请安排保洁清运。 | `[]` | `[]` | **NONE** |

社区核心动词 `维修 / 检修 / 更换 / 清运 / 派单` —— 无一在词表中。

## 二、第二个更根本的障碍：域外默认行为

### 2.1 实测 gateway 对未知类别的响应

```
gateway('维修派单', fact_effective=True)  = ('denied', 'unknown action kind')
gateway('维修派单', fact_effective=False) = ('denied', 'unknown action kind')
```

**注意**：即使 `fact_effective=True`（事实已成立），域外动作仍返回 `denied`。

### 2.2 这个行为在部署中的后果

若社区系统将所有动作送入判定器并采用 **fail-closed** 策略：

```
派单 → 词表未命中 → denied
结单 → 词表未命中 → denied
全部正常工单被阻断
```

且拒绝理由是 **"unknown action kind"（未知动作类型）**，
而非 "fact not effective"（事实不成立）——两者语义完全不同，
前者意味着**能力缺失**，后者才意味着**风险拦截**。

> **"接不住"与"被拒绝"是两回事**：
> 接不住 = 返回空，业务继续；
> denied = 阻断业务。
> 当前原型对域外输入的默认行为是后者，且无 `REVIEW` / `UNKNOWN` 中间态可供降级。

## 三、双向误判（实测确认）

词表跨域使用时，**两个方向都会错**。

### 3.1 该拦的拦不住

```
"请派电工维修楼道灯。"      → danger=[] safe=[]  → NONE
"请更换损坏井盖。"          → danger=[] safe=[]  → NONE
```

### 3.2 不该拦的乱拦

```
"确认恢复楼道照明后关闭工单。"  → danger=['确认恢复']  → dangerous
"垃圾清运完毕，请关闭事件。"    → danger=['关闭事件']  → dangerous
```

两条均为社区**正常结单操作**，却被判为危险动作。
当 `fact_effective=False` 时，返回 `('denied', 'required facts are not effective')`。

**这是实测发现的真实误判，不是理论推演。**

## 四、唯一命中的那条是碰巧（同义替换测试）

| 动词 | 是否命中 safe_probe |
|---|---|
| 请**核实**材料是否齐全 | ✅ 命中 `核实` |
| 请**审查**材料是否齐全 | ❌ NONE |
| 请**核查**材料是否齐全 | ❌ NONE |
| 请**查证**材料是否齐全 | ❌ NONE |

同一语义，换动词即失效。

说明词表为**字面枚举**，非语义匹配。
社区场景口语变化幅度显著大于技术剧本，此脆弱性在社区场景被放大。

## 五、修正后的分层模型

原分析按"数据形态"分层（文本/工单 vs IoT JSON）。
实测表明应按**词表域**分层：

```
第一层（域内，技术剧本）    → 当前原型可直接处理
     例：重启数据库、切换主备、关闭告警

第二层（域外，社区文本）    → 需词表扩展 + 领域适配
     例：维修、更换、清运、派单
     注意：同为纯中文文本，仍不可用

第三层（域外，结构化事件）  → 需协议适配 + 语义转译 + 词表扩展
     例：水表零读数、烟感报警、电梯困人码
```

**关键修正**：第二层与第三层的距离，比原分析估计的近得多——
两者都需要词表扩展，第三层额外需要结构化适配。
原分析将第二层视为"最容易落地"，实测不成立。

## 六、五项可验收能力 × 体元满足度（实测对照）

| # | 能力 | 当前原型状态 | 实测依据 |
|---|---|---|---|
| 1 | 事件可结构化 | ❌ 不具备 | 无 schema，仅正则匹配 |
| 2 | 证据可追溯 | ⚠️ 部分 | #9 已改为真断言；无哈希锚定、无审计 ID |
| 3 | 状态可判定 | ⚠️ 仅两态 | `gateway` 仅返回 `allowed`/`denied`；`REVIEW`/`UNKNOWN` 字符串 0 匹配 |
| 4 | 动作可约束 | ⚠️ 结构具备 | 分支结构正确；仅两档、无风险分级、无降级策略 |
| 5 | 过程可复核 | ❌ 不具备 | `audit`/`rule_version` 0 匹配 |

**五项中完整满足的为 0 项。**

## 七、修正后的定位表述

原建议表述：

> 具备面向社区工单和物联网事件的拟议映射能力；当前尚未完成生产系统接入，
> 需补建设备适配、事件解释、策略执行和审计接口。

**建议修正为**（补入词表域限制）：

> 当前原型为面向数据库运维领域中文文本的冻结回归判定器，
> 其动作词表覆盖范围为技术运维动词（26 项危险 + 20 项只读）。
> 实测确认：社区常见动作（维修、更换、清运、派单）与结单操作
> （确认恢复、关闭事件）分别存在**漏判**与**误判**。
> 因此无论输入为文本工单还是结构化 IoT 事件，
> 均需先完成**领域词表与动作分类重构**，再谈设备适配与策略执行。
>
> 当前尚无任何证据表明已连接社区生产设备或业务应用。

## 八、对三条链路建议的修正

| 原建议顺序 | 实测修正 |
|---|---|
| 1. 物业报修闭环（"最容易实施"） | ⚠️ **不成立**。同为域外文本，实测 6 条中 5 条 NONE。需先扩词表 |
| 2. 智能水表异常核查（"最能证明可计算"） | ✅ 顺序合理，但需同时补结构化适配 + 词表扩展 |
| 3. 电梯困人分流（"最能展示风险治理"） | ✅ 成立，且必须先引入 `REVIEW`/`UNKNOWN` 与风险分级 |

**修正后的最小起步**：先做**词表域扩展 + 四态判定**，
再谈任何链路——否则任何链路都会撞上同一个 NONE/误判问题。

## 九、本文的局限

- 测试文本为人工构造的社区场景样例，非真实工单语料
- 未测试真实工单的口语噪声、错别字、方言影响
- 词表域障碍为实测确认；扩词表后的效果未测
- 本文不证明"体元理论不可用于社区场景"，仅证明**当前原型实现**不可用
